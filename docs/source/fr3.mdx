# FR3 Robot and SensorHub

The `fr3` Robot integrates an FR3 arm, Robotiq gripper, four externally managed RealSense writers,
a dual-Xense writer, and an FT300S writer. The Robot owns only its SensorHub subprocess and its
local command publisher. It never starts or stops the upstream sensor writers, telemetry relay, or
remote command subscriber.

## Scope and startup

An external run controller does not exist yet and is not part of this implementation. Until one is
implemented, an operator or temporary script must start and verify these prerequisites before
starting LeRobot:

1. Four RealSense SHM writers: `/realsense_cam1` through `/realsense_cam4`.
2. The dual-Xense writer: `xense_sensor_frame`.
3. The FT300S writer: `ft300_sensor_frame`.
4. The FGT1 telemetry relay at `tcp://192.168.1.37:6000`.
5. The remote command `SUB` bound to `tcp://*:6001`.

`FR3.connect()` starts SensorHub, which defensively attaches and validates those already-running
sources. Every source must produce at least two coherent, advancing samples, and SensorHub must
publish one aligned snapshot before it reports `READY`. A missing or invalid prerequisite makes
`connect()` fail within the configured startup timeout.

Example CLI selection:

```bash
lerobot-rollout \
  --robot.type=fr3 \
  --robot.id=fr3 \
  ...
```

Install the ZMQ dependency with `pip install 'lerobot[fr3]'` (or the equivalent `uv` command).

## Action and observation interface

Actions contain exactly `fr3_joint1.pos` through `fr3_joint7.pos` in radians and `gripper.pos` on
the policy scale `[0, 1]`. Joint values are not limited in the Robot. The gripper value is clamped,
logged when changed, and converted with `floor(value * 255 + 0.5)`. `send_action()` returns the eight
values actually submitted to the local publisher.

Observations expose joint position, velocity, torque, normalized and raw gripper feedback, FT300S
wrench, two independent `(35, 20, 3)` float32 Xense force fields, four RGB images, and four Z16 depth
images. The FR3 feature adapter declares Xense as numeric Array3D data; it is not encoded as video.
The FR3 policy processor converts online Xense HWC to BCHW and offline BTHWC to BTCHW. It performs
no sensor I/O, alignment, feature encoding, safety control, or CNN fusion.

## Command ABI v1

The Robot uses a latest-only ZMQ `PUB` that connects to `tcp://192.168.1.37:6001`. The remote
controller uses `SUB`, binds `tcp://*:6001`, subscribes to `b""`, and both sides use `CONFLATE=1`,
HWM 1, and `LINGER=0`. Messages are single-part, little-endian, and exactly 112 bytes:

```text
offset  size  field
0       8     magic = "FRCMD1\0\0"
8       4     abi_version = 1
12      4     header_size = 48
16      4     total_size = 112
20      4     flags = 0
24      8     sequence:uint64
32      8     realtime_ns:int64
40      8     monotonic_ns:int64
48      56    joint_targets[7]:float64
104     1     gripper_gPO:uint8
105     7     zero padding
```

PUB/SUB has no delivery acknowledgement. The remote subscriber must be ready first, and its
real-time controller must implement the watchdog/timeout hold behavior; that remote implementation
is outside this repository.

## FGT1 telemetry ABI

SensorHub accepts only 504-byte `FGT1` version 1 frames. Robot source 2 requires valid-mask bit 2
and maps `q=floats[8:15]`, `dq=floats[15:22]`, and `tau_J=floats[22:29]`. Gripper source 3 requires
valid-mask bit 4 and supplies `gPO/gCU`. Their sequences and caches remain independent. GELLO source
1 is ignored.

## AlignedObservation SHM ABI v1

SensorHub owns `/fr3_aligned_observation`. It is a Linux x86-64 little-endian, 8-byte-aligned,
two-slot seqlock mapping with magic `FR3OBS1\0`:

```text
global header  320 bytes
slot header    160 bytes
slot stride    6,161,080 bytes
total size     12,322,480 bytes
```

The global header stores ABI sizes, dimensions, latest sequence, and fatal status/message. The slot
header stores the aligned sequence and publish clocks followed by sequence/source-time pairs for
four cameras, Xense, FT300S, robot, and gripper. Payload order is four RGB arrays, four depth arrays,
two Xense fields, wrench, q, dq, tau_J, normalized gripper position, gPO, gCU, and six padding bytes.

For snapshot `L`, slot `L % 2` is stable only when its seqlock equals `2 * L`. A reader copies the
whole slot and checks the seqlock again. The Robot returns arrays backed by that independent local
copy, so a later SensorHub publication cannot overwrite data already handed to a policy thread.

## SensorHub control and failure behavior

The control socket uses `AF_UNIX/SOCK_SEQPACKET`. Each JSON packet is at most 512 bytes and contains
exactly `protocol_version`, `type`, `sequence`, `timestamp_ns`, `status_code`, and `message`. Types are
`READY`, `HEALTH`, `FATAL`, `PING`, `PONG`, and `SHUTDOWN`.

All modalities are required. There is no reader reconnect, SHM remap, local recovery, or automatic
SensorHub restart. A stale source or sustained alignment failure marks the aligned SHM fatal, sends
`FATAL`, stops publication, and exits SensorHub. `FR3.disconnect()` requests `SHUTDOWN`, then escalates
to process-group `SIGTERM` and `SIGKILL` if necessary. It does not signal external writers, the relay,
or the remote controller.

## Future external controller contract

The future controller should start writers, relay, and remote subscriber; verify their ABIs and
advancing sequences; start LeRobot; monitor every required component; and terminate the whole run on
any fatal error. This is an interface contract only—no external controller is implemented here.
